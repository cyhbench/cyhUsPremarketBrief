## 2. 時間模型與執行期限

### 2.1 日期、時區與 DST

- 所有運算使用帶時區的時間；Python 使用 `zoneinfo.ZoneInfo('America/New_York')` 與 `Asia/Taipei`，UTC 作為儲存時間基準。缺少時區資料就停止，不退回固定 UTC offset。
- 一次執行固定一個 `report_date`：由啟動時的紐約日期取得。檔名、日曆、新聞篩選與報告標題都使用它，不能用宿主日期或 UTC 日期替代。
- 開盤時間是該交易日的紐約 09:30；09:00、09:15、09:24、09:25 等時間均先在同一個紐約日期建立，再換成 UTC 比較。不要以台灣日期加減 12／13 小時拼出時間。
- EST／EDT 由當日時間物件產生，不固定寫 EST；台灣時間附完整日期，避免晚間經濟事件換算後跨日仍只寫時分。
- 持久時間欄位使用帶 `Z` 或 offset 的 ISO 8601；顯示同時附時區名稱或縮寫。不要只寫容易混淆的 `CST`。

本次以本機 `systemd-analyze calendar` 實測的排程結果如下，均為美東 09:00：

| 美東日期 | UTC | 台灣時間 | 用途 |
|---|---|---|---|
| 2026-10-29、10-30 | 13:00 | 當日 21:00 | 秋季切換前 EDT |
| 2026-11-02 | 14:00 | 當日 22:00 | 秋季切換後 EST |
| 2027-03-11、03-12 | 14:00 | 當日 22:00 | 春季切換前 EST |
| 2027-03-15 | 13:00 | 當日 21:00 | 春季切換後 EDT |

保留 spec 的 `OnCalendar=Mon..Fri *-*-* 09:00:00 America/New_York` 與 `Persistent=false`。timer 只是喚醒器，是否為交易日仍由腳本判斷。明確設定小的 `AccuracySec`、不加隨機延遲；不靠變更系統時鐘、系統時區或校時服務測 DST。

### 2.2 絕對期限與程序管理

| 時間（當日美東） | 允許的工作 |
|---|---|
| 09:00 前 | 正式模式不產生或發布；測試使用隔離模式 |
| 09:00–09:15 | Claude 最多一次；提前失敗即可立刻切換，不等到 09:15 |
| 09:15–09:24 | 僅供已需要的 Codex 備援與結果收尾；Codex 提早啟動仍以 09:24 為上限 |
| 09:24–09:25 | 最終驗證、寫檔、commit、push；09:24:30 前開始 push，保留至少約 30 秒網路餘裕 |
| 09:25 起 | 禁止正式報告／清單的新寫入、commit 或 push；只確認既有發布結果、記錄、清理與通知 |
| 09:25–09:30 | 確認 Pages 是否顯示當天內容；09:30 仍未確認則回報發布未完成 |

上表是最晚期限，不要求等待到該時段才進下一步。Claude 或 Codex 提早成功，就立即驗證並發布。

- 正常生成啟動窗口為 `[09:00, 09:15)`；若 timer 異常延遲到 09:15 才啟動且沒有可恢復的既有產物，停止並記錄 `MISSED_START_WINDOW`，避免無預算仍啟動 Claude。恢復既有產物依第 7 節，不重新產報。
- 每一個 Git／AI 子程序都設 timeout，不只 AI。AI 啟動、MCP 連線、格式檢查、程序清理均計入預算；不能另起一個「完整九分鐘」的 Codex 而越過 09:24。
- 每次等待取「階段截止前剩餘秒數」與總剩餘預算較小者；用 monotonic clock 計算耗時。每個發布動作前再檢查實際牆鐘，牆鐘異常跳動或系統休眠甦醒後已逾期就停止，不調整時鐘補救。
- 逾時先終止該次 AI 程序群組，短暫等待後只清理仍存活的本次子程序，再啟動備援。不得以名稱批次殺掉其他 Claude、Codex、Brave 或 bot 程序。
- AI 回覆、stdout、stderr 均有大小上限；建議報告上限 128 KiB。無限輸出視為該次生成失敗，避免耗盡記憶體或磁碟。
- 09:25 是本機停止發布操作的期限，無法保證遠端服務的原子截止：push timeout 時 GitHub 仍可能已接受。此時標記「發布狀態待確認」，不聲稱「確定未發布」。Pages 在 09:30 前可見是實測目標，不能靠程式 timeout 保證。

### 2.3 資料時間與跨日

- ForexFactory XML 的 UTC 語意目前僅由 spec 的單一實測支持，不能視為來源永久契約。實作前以至少一個 EST 與一個 EDT 已知時間事件對照；通過後在 prompt 明定輸入時區。來源時間語意有衝突時標示無法確認，不猜 offset。
- XML 先把完整「日期＋時間」解析為來源時區，再轉美東篩當日。不能先依 XML 日期過濾；若跨週邊界且 thisweek 不含必要日期，標資料範圍不足，不能當成零事件。
- `All Day`、`Tentative` 等無精確時間事件不能換算時分。保留原文與來源日期；若無法證明它屬於哪個美東日期，另列「日期／時間待確認」，不宣稱今日沒有重大事件。
- ForexFactory 網頁不可假設每次都仍顯示台灣時區。每次瀏覽先確認實際顯示時區；取目標美東日 `[00:00, 次日00:00)` 換到該時區所跨的所有日期，連續空白時間列只在同一日期群組內沿用上一個明確時間。
- XML 與網頁事件用名稱、幣別、時間共同對照，不能只憑相同事件名稱套實際值；區分實際值為零、空白、尚未公布、抓取失敗與修正前值。
- 「過去 24 小時」從該次實際擷取時間回推，使用絕對時間，不能只比來源當地日曆日期。報告是 09:00 起生成的快照，不是所有來源同一秒的快照。
- 報價區分來源資料時間與本次擷取時間。Mag 7 只有當日 `PRE_MKT` 且資料時間合理時才列為當日盤前；`POST_MKT` 不能冒充盤前。盤前失敗仍按 spec 列已確認的前收與缺值標記。
- 亞太市場的最近收盤依各來源實際交易日期呈現。沒有當地交易日曆或明確休市資訊時只寫「最近可得收盤」，不能由舊報價推定當地休市。

## 3. NYSE 日曆與上一交易日

### 3.1 日曆資料契約

採用 `data/nyse-calendar.json`，不引入交易日曆套件。建議資料包含：`schema_version`、`timezone`、`source_url`、`verified_on`、`coverage_start`、`coverage_end`，以及逐年完整的 `closed_dates`、`early_closes`。日期採 ISO 日期；早收時間採美東時分及原因。保留可記錄官方特殊停市／改時的例外欄位，不新增即時抓日曆服務。

載入時驗證：年份完整覆蓋、日期合法、無重複、早收與全休不衝突、收盤晚於開盤、時區為紐約。非週末且不在完整覆蓋年度的休市表內，才判定一般交易日。週末可直接略過；平日日曆缺漏或無效屬 `CALENDAR_UNKNOWN`，停止並通知，與已確認的休市不同。

官方頁面本次已列 **2026–2028**，spec 說列 2025–2027 已過時。首版仍照 spec 維護 2026、2027，不因此擴大年度範圍；但跨年復盤需要前一年的尾端資料，不能默認缺的年份都是平日交易。

以下是本次從 [NYSE 官方頁面](https://www.nyse.com/trade/hours-calendars) 核對的初版抄錄對照，仍須實作者逐項核對產出的 JSON：

| 年度 | 全日休市（美東日期） | 13:00 早收 |
|---|---|---|
| 2026 | 01-01、01-19、02-16、04-03、05-25、06-19、07-03、09-07、11-26、12-25 | 11-27、12-24 |
| 2027 | 01-01、01-18、02-15、03-26、05-31、06-18、07-05、09-06、11-25、12-24 | 11-26 |

不能套用所有聯邦假日、通用補假函式或「國定假日前一天都早收」：2026-07-03 是全休，2027-12-24 也是全休；官方註明 2028-01-01 週六不補休，因此 2027-12-31 為一般交易日。早收日仍於 09:30 開盤，產報時間不變，報告註明 13:00 ET 收盤及完整台灣日期時間。

靜態日曆只反映最後人工核對的官方公告，**無法自動偵測之後宣布的臨時休市**。維護者需更新例外；若營運要求自動涵蓋臨時公告，需另議範圍與可靠來源，本次不假裝已解決。

### 3.2 復盤的兩種日期

- `previous_session_date`：在完整日曆內倒查的上一個 NYSE 交易日，不能用「昨天」或「週一就減三天」。例如 2026-11-27 的前一交易日為 11-25。
- `baseline_report_date`：從已確認推送的清單選出嚴格早於今日的最新報告；不按檔案 mtime，不含本機未發布產物。
- 兩者不同時分開呈現：上一交易日收盤照實列；對照的是哪一天的盤前報告另寫明，並列出缺報的交易日，不把中間週末或休市算成缺報。
- 舊報告的待公布事件對照該報告日期的實際值；上一交易日的數據另按 `previous_session_date` 查。不能把兩個日期的同名事件或 Mag 7 收盤混在一起。
- 前收資料時間必須符合目標交易日，早收日以當日早收盤為準。日期不符就標示最近可得資料與缺值，不將更舊價格稱作上一交易日收盤。
- 首次執行沒有歷史報告不是失敗。跨年無足夠日曆可判定上一交易日時，復盤該部分標「日曆覆蓋不足，無法確認上一交易日」，仍可產生當日日曆已確認的報告；不虛構前一日。待日曆補齊才補足此功能。

## 4. Claude → Codex 的判斷

### 4.1 判斷「這次能否用」，不猜「帳號剩多少額度」

需求指定 Claude 額度用完改 Codex，spec 進一步採用其他生成失敗也備援。本設計採 spec 的單次生成備援方式，**不新增額度查詢、不解析自然語言猜帳號狀態、不永久切換預設供應者**。每個交易日重新先試 Claude。

成功必須同時符合：程序正常結束、輸出協定可解析、沒有協定明示錯誤、最終報告非空且通過第 6 節。退出碼 0 本身不代表成功；含錯誤 JSON、只有「額度不足」文字或截斷內容都不是快報。

Claude 以 JSON 的最終結果為輸入，解析 `result` 與版本支援的錯誤欄位（例如 `is_error`）；不把完整 JSON、stderr 或工具 transcript 當報告。未知 envelope 結構停止接受該次結果，不能猜取其中一段文字。CLI 版本與已測成功／失敗樣本構成解析契約。

只有已觀察且有文件或樣本支持、可機械判讀的 quota 錯誤類型，才記為 `CLAUDE_QUOTA_EXPLICIT`；一般 429 可能是短暫限流，不足以證明訂閱額度耗盡。其餘記錄 `CLAUDE_EXIT_ERROR`、`CLAUDE_TIMEOUT`、`CLAUDE_PROTOCOL_ERROR` 或 `CLAUDE_REPORT_INVALID`。無真實額度耗盡樣本前，該分類列為未驗證，仍能依其他失敗安全備援。

| 情況 | 是否啟動 Codex | 後續 |
|---|---|---|
| 明確 quota、Claude 非零退出／無法啟動、Claude 自身登入失敗 | 是，時間與 Codex 預檢允許時 | 記錄真實分類，不把全部說成 quota |
| 退出 0 但 `is_error`、空白、錯誤協定、缺標題／錯日期 | 是 | 丟棄整份 Claude 候選，不拼接兩個 AI 的文字 |
| Claude 逾時或瀏覽失敗原因不明 | 是，先清理本次程序與瀏覽工作階段 | 至多一次備援，不對同一供應者無限重試 |
| 個別來源抓不到，但報告完整且有其他有效來源 | 否 | 依 spec 標缺值後發布，避免為缺一項重做整份 |
| 所有來源皆無法取得，沒有有效來源連結 | 是，若非已確認共用故障 | 兩者都如此則失敗，不以來源名稱湊數通過 |
| 已確認 Brave 啟動失敗／工具白名單失效、日曆錯誤、Git 失敗、權限不足 | 否 | 共用前提有問題，停止；切模型不能修復或繞過 |
| 剩餘時間不足或已過模型截止 | 否 | 記 `DEADLINE_EXCEEDED`，不啟動注定逾期的工作 |

Claude 失敗但 Codex 成功不通知，符合「成功不通知」；只記一次 fallback 原因。Codex 也失敗時發當日最終失敗通知。Codex 的輸出檔由 CLI 宿主寫入，不授權模型寫本機；仍檢查退出狀態、最終結果與格式，不使用過去執行遺留的檔案。

## 5. AI 與瀏覽器邊界

採用 spec 的一次性 CLI、新空暫存工作目錄、前一份報告由包裝器注入、Git 完全由包裝器執行。提示詞以 stdin 傳入，分隔「可信規則」與「不可信歷史報告／網頁資料」，不把網站中的操作指示當成命令。

### 5.1 有效工具集合才是判準

- Claude 保留 `--tools ""`；MCP 只載入本次 Brave，使用明確工具白名單，不以整個 `mcp__brave` 萬用放行當作完成安全設計。停用本次不需要的 hooks、skills、plugins 與 session persistence，避免繼承個人自動化。不得以 `--bare` 草率替代，因其登入方式可能不同，需維持既有已授權登入。
- Codex 保留 `--ignore-user-config`、shell 關閉、唯讀與永不要求核准；另外明確關閉內建 `web_search`，停用非本次所需的 apps、額外 MCP、程式執行與多 agent 能力。工具清單若仍可讀檔、改檔或執行程式，就不符合「只瀏覽」，不能只靠提示詞禁止。
- 本次官方文件確認 `features.shell_tool` 只控制命令執行，`sandbox_mode` 也不是所有 MCP 的能力白名單；MCP 應用 `enabled_tools` 指定允許工具，`disabled_tools` 再封鎖。不得由「讀 `/etc/hostname` 一次失敗」推論不存在其他讀檔管道。
- Brave 最小集合涵蓋導覽、snapshot／find、必要的 click／文字輸入／分頁及 `browser_close`。不開放檔案上傳、任意程式執行、安裝瀏覽器、讀本機或可設定輸出檔名寫檔的能力；如必要工具有這類參數，須有工具層的參數限制或縮減介面，不能靠模型自律。
- 禁止 `file:`、本機／私有網段網址與未知下載；資料只走 Brave，不改用內建搜尋、WebFetch 或 shell HTTP 取網頁。一般搜尋從 Brave Search 起；已知來源可直接導覽。
- 不掛載私人 Brave profile、不匯入 cookies／登入資料。記錄共用 `bot_browser` 模組與 CLI 的實測版本；只引用、不修改共用模組。模組更新後重新檢查有效工具，不能假設行為不變。

本次只讀確認：Claude Code `2.1.308`、Codex CLI `0.164.0`；`--help` 列有 spec 所需主要輸出參數。**沒有重新驗證正式呼叫的有效權限或額度失敗格式**。Codex help 曾提示無法建立 PATH aliases（唯讀檔案系統）；不以提權或改設定處理，也不因此宣稱完整產報可用。

### 5.2 工作階段生命週期

Claude 與 Codex 必須各用乾淨的瀏覽工作階段；每次完成、失敗或取消都執行 `browser_close`，清除 cookies 與網站儲存。timeout 後須由本次宿主清理保證關閉，不能期待已終止的模型自行收尾。

若共用瀏覽器無法提供獨立工作階段或可靠互斥，可能與 Telegram 使用者的瀏覽工作互相關閉分頁；此時停止排程上線，不修改既有 bot 解決。單一報告檔案鎖只能避免本專案重複執行，不能證明已與其他 bot 的瀏覽作業隔離。

包裝器不將通知 token、chat id、Git credential 或完整環境變數傳入提示詞；通知秘密在需要通知時才由受信任宿主存取。CLI 登入仍須由既有授權機制取得，不能把「模型看不到秘密」誤寫成「CLI 程序不需要登入」。

## 6. 報告、清單與驗證契約

### 6.1 分工與資料形狀

- AI 唯一產出為 UTF-8 Markdown 本文。包裝器提供可信的美東日期、開收盤時間、前一交易日（若可確認）、baseline 日期與內容、來源規則及 deadline。
- 標題與七個內容標題、資料來源標題照 spec 4.4，合計九個。各必須在正確層級且只出現一次，順序固定；code fence 裡的假標題不能計入。
- 日期、產生者及美東／台灣產生時間由包裝器在模型完成後組成或核對，再通過完整驗證；不信任模型宣稱自己是哪個供應者。產生時間與各項資料時間分別呈現。
- `reports/index.json` 建議為 `schema_version` 加按日期遞減的 `reports` 陣列；每筆含 `date`、`generated_at`（UTC ISO 8601）、`producer`（`claude`／`codex`）。日期唯一，網址一律由日期推導，不另存可任意注入的 path 或重複的 latest 指標。
- 清單只列已納入同一發布 commit 的報告；AI 不修改清單。不掃描工作目錄所有 `.md` 來猜最新報告，避免納入未發布候選。

### 6.2 兩層檢查

**阻擋發布的機械檢查**：

1. CLI 成功協定、非空、UTF-8 合法、大小上限，無 NUL 或不允許的控制字元。
2. 當日交易日、標題日期、九個標題與順序、可信產生者、雙時區時間一致。
3. 七節都有內容；數據節須有預期項目的資料或明確缺值，而非只有標題。亞太六項、期貨三項、Mag 7 七檔都有交代；新聞與經濟數據可使用 spec 規定的無資料敘述。
4. 資料來源至少有一個有效 `https:` 連結，且是本次讀取成功來源的聲明；不能只放來源名稱、空標題或失敗來源。機械檢查只能驗證聲明的結構，不能證明模型真的讀取成功。
5. 拒收明確未替換的 `X.XX`、`HH:MM` 等範本 token；**不能一律禁止方括號**，否則正常 Markdown 連結也會被擋。
6. 以既有核准掃描器檢查待發布內容；檢查失敗就停止，不把命中片段印到公開 log。掃描器不可用時不能宣稱已完成秘密檢查。

**仍需抽查的語意檢查**：數字正確、來源時間與市場狀態、來源確實成功、新聞摘要不誤導、沒有捏造驅動因素。格式合法不能證明這些事；沿用 spec 的三日資料抽查，保存當次必要的公開來源證據，不能隔天用最新報價反查昨天盤前數字。

單一資料源失敗是內容降級，不是流程失敗；日期不明的數字不當作今天數字。模型把「缺值」寫得很完整也不能繞過至少一個有效來源要求。若全部來源不可得，保留網站上一份報告並通知失敗。

## 7. 執行、發布與恢復

### 7.1 受信任包裝器流程

1. 建立 `run_id`、固定當日日期與期限；取得整次執行的非阻塞檔案鎖。另一個執行持鎖時安靜退出，不重複通知；已確認週末可直接略過，平日則同步後才依日曆作最終判斷。
2. 確認專案、預期分支 `main`、遠端 repo 身分、乾淨 index／工作目錄及沒有未識別的待推 commit。髒工作目錄不自動 stash、reset、clean 或 add；停止並說明。
3. 有 timeout 的 `git pull --ff-only`；失敗就停止。**pull 後重讀**日曆、prompt、報告清單與當日發布狀態，確認休市即安靜略過，避免遠端已產出仍重做，也避免使用過時日曆。此順序意味著平日無法同步時不能確認最新休市表，按同步失敗處理，而非猜測為休市。
4. 處理第 7.2 節的已有產物；需要新報告時讀取已推送的最新舊報告並檢查清單與檔案一致，才啟動 Claude／必要的 Codex。
5. 候選先留本次私有暫存，不動正式報告。通過第 6 節後，檢查時間、工作目錄仍符合預期、當日正式檔尚不存在。
6. 以獨占建立保護當日報告不覆寫；清單先寫同目錄暫存再原子替換。兩個檔案跨檔案沒有真正原子性，靠檔案鎖、候選驗證、Git 同一 commit 與恢復狀態保護。
7. 只 stage `reports/YYYY-MM-DD.md` 與 `reports/index.json`，核對 staged diff 的實際兩個路徑、內容及秘密掃描；有額外變更就停止。commit message 沿用 `brief: YYYY-MM-DD (claude|codex)`，不加 AI 署名。
8. commit 前再檢查期限；commit 後記錄 commit id 與產物摘要。有 timeout 地 push 到已確認的 `main`，不 force、不自動 rebase 或解衝突。
9. 確認遠端分支包含目標 commit，才記 `PUSH_CONFIRMED`；接著透過 Brave 確認 Pages 的清單含當日，報告本文等於當次產物，才記 `PAGES_VISIBLE`。各階段耗時分開記。
10. 不論結果均清理本次瀏覽工作階段與子程序、釋放鎖；流程失敗統一走一次通知。不得刪除未知檔案或其他程序的工作階段。

### 7.2 狀態與重入

狀態記錄只提供恢復線索，不能取代重新核對 Git 與檔案內容。至少區分 `SKIPPED_CLOSED`、`GENERATING`、`VALIDATED`、`COMMITTED_LOCAL`、`PUSH_CONFIRMED`、`PAGES_VISIBLE`、`FAILED`、`PUBLISH_UNKNOWN`。

| 重跑時狀態 | 行為 |
|---|---|
| 當日已在遠端，清單與內容一致 | 不再生成或 commit；必要時只確認 Pages |
| 有可辨識的本次本機 commit，遠端尚無 | 只有在期限內、遠端仍可 fast-forward、commit 僅含預期兩檔時，允許一次明確重跑只推既有 commit |
| push 回傳錯誤／逾時，遠端狀態不明 | 用 GitHub／Git 唯讀確認；已收到就不再 commit，無法確認就 `PUBLISH_UNKNOWN`，停止盲目重送 |
| 有當日檔案但沒有可信對應 commit／狀態，或只有一個檔寫好 | 停止，保留證據供人工處理；不以存在即成功，也不刪檔重做 |
| 遠端有別人新增 commit／發生非 fast-forward | 保留本機產物，停止並通知，不 force 或自行解衝突 |
| 超過 09:25 | 不再推送今天或過期報告；本機未推 commit 留待人工處理，次日預檢也須擋下，避免連帶推送昨天的盤前報告 |

本機 commit 成功而 push 失敗時不能 reset 清掉；通知明示「本機已有 commit，未確認推送」。若遠端已推但 Pages 逾期，通知為「已推送，網站尚未確認更新」，不能統稱「未發布」。

### 7.3 Pages 與快取

`fetch(..., {cache: 'no-store'})` 保留；它控制瀏覽器快取，不能使尚未部署或 CDN 舊內容立即更新。清單與報告發布於同一 commit，但不同資源仍可能暫時讀到不同版本。

檢視器遇到清單新、報告 404 或日期不符，顯示「報告更新中，請稍後重試」，不顯示空白頁或把舊文標為今天。預設顯示最新已取得報告並清楚顯示日期；當天生成失敗時不會修改網站，所以舊報告日期必須醒目。歷史報告保持當時數字，不事後回填。

Pages 首次啟用、權限、部署方式與耗時仍需後續獲授權的部署驗證；本次不改 repo 設定。只看到 GitHub deployment 成功還不等於實際頁面已更新，驗收仍需用瀏覽工具讀到當次內容。

## 8. 靜態檢視器

維持單一 `index.html`，`marked` 鎖 spec 指定版本，不新增後端。Markdown 來源一律不可信：

- 原始 HTML 以純文字顯示，包含標籤、事件屬性與 SVG，不能先渲染再靠刪 `<script>` 補救。
- 連結解析 URL 後只准 `https:`，拒絕含憑證、控制字元、`javascript:`、`data:`、`file:` 等；對文字與屬性分別正確跳脫。新視窗連結設定 `noopener noreferrer`。
- 不載入報告內的外部圖片、iframe 或嵌入內容；Markdown 圖片顯示替代文字，避免自動追蹤與額外外連。
- 日期選單來自經驗證清單；日期通過實際日期合法性檢查，再由前端拼出固定 `reports/YYYY-MM-DD.md`。不接受清單任意網址、路徑穿越或 AI 提供的 HTML 作為選單。
- 區分首次尚無報告、清單讀取失敗、格式不合法、報告不存在與 CDN 更新中；錯誤以 DOM 文字呈現，不插入不可信 HTML。
- 手機／桌面、系統深色模式沿用 spec。時間顯示固定報告記載的美東與台灣時間，不依讀者電腦時區重新解釋報價日期。

## 9. 錯誤、通知與本機資料

### 9.1 錯誤處理

| 類型 | 處理 | 通知 |
|---|---|---|
| 確認週末／休市、另一程序持鎖、已成功推送 | 略過，不執行 AI | 無 |
| 單來源失敗／沒有歷史報告 | 報告內明確標示，繼續 | 無 |
| 日曆未知、設定錯誤、髒工作目錄、pull 失敗、共用安全前提失效 | 不產生／不發布 | 一次最終失敗通知 |
| Claude 失敗、Codex 成功 | 發布 Codex 結果 | 無 |
| 雙模型失敗、無有效資料、逾期 | 不新增發布 | 一次最終失敗通知 |
| push／Pages 狀態不明或未完成 | 保留本機產物，明示已知階段 | 一次對應狀態通知 |
| 通知不可送達 | 保留失敗退出與本機／journal 記錄 | 不遞迴通知、不無限重試 |

以集中收尾處理錯誤，避免每層 catch 各發一則。通知介面輸入為日期、穩定原因碼、安全摘要與本機記錄路徑，不傳原始 stderr、報告、完整 URL query 或 credential。沿用 spec 的失敗通知格式，但依第 7 節區分「未產生／未確認推送／已推但網站未更新」。

一般通知只有一次送出嘗試，設定短 timeout；Telegram HTTP 成功仍須檢查回覆 `ok`。回覆無法確認時記錄 `NOTIFY_UNKNOWN`，不自動重送造成重複訊息；「恰好送達一次」不是無法控制網路下可保證的性質。跨重跑只在狀態紀錄顯示未嘗試時再嘗試，通知送達未驗證不算驗收通過。

### 9.2 存放與保護

- 公開 Git 只放網站、prompt、官方日曆、報告與清單；不放 token、chat id、原始 CLI transcript 或私人設定。
- spec 的 repo 外 config／state 路徑是未來部署提案；目前只允許改專用工作目錄，本步不建立它們，也不動既有 bot 程式、設定或秘密。未來部署須先核對當時授權與環境限制。
- 狀態紀錄與 log 包含 `run_id`、美東日期、階段、CLI／模組版本、供應者、錯誤碼、耗時、commit id 及來源可得性。無法由工具紀錄確認的來源狀態記 `unknown`／`model_reported`，不能把模型列出的來源冒稱實際探測結果。
- 原始 stderr／transcript 不預設永久保存；必要診斷資料先移除秘密與控制字元，僅保留本機。既有 log 不整批覆寫。
- 一次執行的暫存使用空的系統暫存工作目錄，權限僅限擁有者，結束清除本次資料。本次不建立暫存或變更環境。跨 session 可重建測試產物若要放專案外，遵守 `cyh-env` 的 `CYH_SCRATCH/<專案名>/`；未設定或路徑不存在就停止，不自選持久快取位置。不可重建的發布恢復紀錄不當成可隨時丟棄的快取。
- spec 6.1 的工作樹掃描不能證明 Git 歷史無秘密；首次發布前需另查可達 commit／blob。掃描工具還需用獨立、非真實秘密的正向樣本證明會命中，不能只憑 0 或空結果宣布安全。

## 10. 上線前阻擋與尚待驗證

以下是實作／部署前提與審查發現，不是已新增的使用者決定。本次不因此修改 spec 的「已決定」。

1. **通知通道：VM 互動 shell 已實測送出，正式 systemd 排程環境未驗證**：原先「通知通道與網路限制衝突」的判斷來自當時執行設計審查的 Codex bot 沙箱，其 shell 網路只允許 `api.github.com` 與 `github.com`；這項限制不能直接套用到 VM 互動 shell 或正式排程環境。依 [progress.md 第 2 節第 1 點](progress.md#2-design-第-10-節阻擋項逐條處理)，Claude Code 在 VM 互動 shell（非 Codex 沙箱）已實測 Telegram 通知送出成功，API 回 `ok: true`；該紀錄未留下可核對的去識別 API 回應或收件紀錄。原先將通知視為部署阻擋、要求另找通知途徑或部署環境的判斷已不適用；目前狀態是「互動 shell 曾送成功，正式 systemd user service／timer 環境未驗證」，上線前仍需在正式排程環境實測，不據此宣稱正式通知已通過或受網路限制阻擋。
2. **只瀏覽的權限驗證**：spec 已承認封鎖 upload 尚未驗；還需驗證其他本機讀寫／執行管道及 CLI 繼承設定。若現有共用介面無法表達必要白名單，回報具體缺口，不修改共用模組擴權。
3. **Brave 工作階段隔離**：確認排程不會關閉 Telegram bot 的瀏覽工作階段，且逾時也能清理。沒有此證據就不以「新空目錄」代替瀏覽器隔離。
4. **資料語意與可用性**：沿用 spec 5.4 的盤前型別、08:30 實際值、RSS 新鮮度與耗時試跑；增加 XML EST／EDT 對照。沒有實際 quota 樣本就只宣稱一般失敗備援已測，不宣稱 quota 分類已測。
5. **Pages 與時間目標**：未驗證網站已開啟、push 到可見的實際耗時。先確認一般流程可在 09:25 前推送、09:30 前實際看到當天報告，才啟用每日排程。
6. **既有機器限制**：部署不得修改時鐘、校時服務或既有 bot；不得讀寫 `~/diag/` 或改 SSH 授權。本次未操作任何服務與上述位置。

## 11. 測試策略與交接

### 11.1 可重現、無外部副作用的測試

Claude 實作時先針對可明確判斷的時間、日曆、備援與發布狀態行為建立失敗案例，再補最小實作。以下是預定測試，**本次沒有撰寫或執行這些程式測試**。

時間透過注入 clock 與 monotonic 來源測；供應者、Git、通知與瀏覽器使用可替換的 adapter。日期覆寫只能在隔離測試模式啟用，同時禁用真實 push／通知，不能讓正式模式靠偽造日期發布。測試 CLI 用 fixture 回覆，不消耗真實 AI 額度。

| 測試組 | 最小案例與預期 |
|---|---|
| DST／宿主日期 | 第 2 節六個切換日期；UTC／台灣宿主下結果相同；台灣已隔日但紐約仍前日，檔名仍用紐約日；缺時區資料停止 |
| 截止邊界 | 08:59:59 不產報、09:00 可啟動；09:15 不再啟動 Claude；09:24 AI 結束；09:24:30 不新啟 push；09:25 不 commit／push；程序 timeout、休眠跨過期限及牆鐘跳動均不晚發 |
| 日曆 | 2026-11-26 全休、11-27 早收、11-28 週六；07-03 補休；2027-06-18／07-05／12-24 全休；2027-12-31 正常開盤；未知年度、JSON 損壞、重複／衝突日期停止 |
| 前一交易日 | 2026-11-27 → 11-25；2027-01-04 → 2026-12-31；沒有歷史報告、缺一日報告、跨年日曆不足分別處理，不把休市算缺報 |
